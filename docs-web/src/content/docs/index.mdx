## Why yarcl exists

Picking a component library usually means adopting its design system. You get its sizes, its variants, its idea of what a button or a table looks like, and a theming layer that lets you change colors, fonts and spacing. Everything else is fixed.

So when your design has an `xs` button, a `quiet` variant, square inputs next to pill-shaped buttons, or a table denser than the library's, you're fighting the framework: overriding its CSS, wrapping its components, or passing strings its types can't check. The product ends up looking like the framework with a new paint job, because the framework decided what exists and how it looks.

That's backwards. Your design system is yours: your designers decide which sizes exist, what each variant looks like, how dense a table is, how focus is shown. A component library should provide the hard mechanics (accessibility, keyboard support, positioning, state) and let you define everything else.

yarcl works that way. Your config doesn't just theme the library, it **defines** it:

- **What exists**: which sizes, colors, radii, variants, spacing steps and densities there are, not only their values.
- **The API**: `size` accepts exactly your sizes. Remove a key and every place that uses it stops compiling.
- **The look**: fonts, borders, shadows, focus rings and how each variant is drawn.
- **The defaults**: globally and per component, so buttons can be square while cards are round.

The same components can become [four completely different products](/theming/bundled-themes/), as the demo above shows.

## The injection point

Everything hangs on one import inside the library:

```ts
// inside yarcl
import type config from '@yarcl/config';

export type Size = keyof (typeof config)['sizes'];
export type Color = keyof (typeof config)['colors'];
```

`@yarcl/config` isn't a real package. It's an injection point that two tools resolve to **your** file:

```ts title="vite.config.ts"
plugins: [yarcl({ config: 'src/yarcl.config.ts' })] // runtime values and generated CSS
```

```json title="tsconfig.json"
"paths": { "@yarcl/config": ["./src/yarcl.config.ts"] } // types
```

It's dependency injection at the type level. The library is compiled against your config, so its props accept exactly your keys, its components render your values, and the build generates CSS for them. There's one source of truth, and if the wiring is missing you get a loud error, not silently wrong defaults. [Why an alias and not module augmentation or codegen?](/reference/architecture/)

## What you get

  <Card title="Your config is the contract" icon="seti:config">
    Keys become the only valid prop values. Rename a size and every stale usage is a compile error, including the defaults inside the config itself.
  </Card>
  <Card title="Styles generated at build time" icon="rocket">
    CSS variables and one class per key. Components only set class names: no inline styles, no runtime theming, strict CSP and SSR friendly.
  </Card>
  <Card title="Light and dark from one file" icon="moon">
    Every color is a `light-dark()` pair. Text colors are computed for contrast, and the build warns when a color fails WCAG AA.
  </Card>
  <Card title="Controls that line up" icon="setting">
    Buttons, inputs, selects, checkboxes and tabs share one size scale, so controls of the same size always have the same height.
  </Card>
  <Card title="Opinions per component" icon="pencil">
    `components: { Button: { radius: 'square' } }` makes every button sharp without touching a single call site.
  </Card>
